# Telegram Personal Auto Poster — Render Deployment

Node.js + GramJS dashboard. Posts are sent by your own Telegram account. The control bot only controls the system.

## Deploy on Render

1. Push this project to a **private GitHub repository**.
2. In Render, choose **New + → Blueprint** and connect the repository.
3. Render reads `render.yaml` and creates a Node Web Service with a 1 GB Persistent Disk mounted at `/var/data`.
4. In Render Environment settings, fill:
   - `API_ID` and `API_HASH` from `my.telegram.org` → API development tools.
   - `DASHBOARD_PASSWORD`: a long unique password.
   - `BOT_TOKEN`: token from `@BotFather`.
   - `BOT_OWNER_ID`: your numeric Telegram user ID.
   - `SESSION_ENCRYPTION_KEY` is generated by the Blueprint. Keep it unchanged after login.
5. Deploy, open the Render URL, enter the dashboard password, and connect your personal Telegram account.
6. Open your control bot in a private chat and send `/start`.

## Persistent storage is required

SQLite database, uploaded images, and encrypted Telegram session are stored under `/var/data`. Render's Persistent Disk keeps them across restarts and deploys. Do not remove the disk or change `DATA_DIR`.

**Render Persistent Disks require a paid web service plan.** A free instance has an ephemeral filesystem and is not suitable for retaining SQLite/session/uploads across restarts. A stopped or sleeping service cannot send scheduled posts while offline.

## Local setup

Requires Node.js 20 or newer.

```bash
npm install
cp .env.example .env
npm start
```

For local development, `DATA_DIR=./data` is fine. Generate a strong random `SESSION_ENCRYPTION_KEY`; do not change it after a session is saved unless you intend to log in again.

## Recovery and stored data

- `data.sqlite`: groups, schedules, and post history.
- `uploads/`: uploaded images.
- `telegram-session.enc`: AES-256-GCM encrypted Telegram session.
- On restart, the app reads the encrypted session and attempts to reconnect.
- Scheduled posts remain in SQLite. Overdue posts are eligible to run after service recovery and Telegram reconnection.
- Back up the Persistent Disk regularly.

## Features

- Personal Telegram account login with OTP and optional 2FA.
- Add/remove public groups.
- Text and image posts.
- One-time and repeating schedules.
- Post history.
- Telegram control bot: `/status`, `/groups`, `/addgroup`, `/removegroup`, `/post`, `/schedule`, `/history`, `/pause`, `/resume`, `/stop`.

## Permission and safety notes

Your personal account must be a member of each destination group and must have permission to post. Public does not mean everyone can post. This app does not bypass group restrictions. Respect group rules and Telegram rate limits; do not use it for spam or unsolicited bulk posting.

Each schedule targets one group; create one schedule per group. Image upload limit is 10 MB.


## Firebase session storage (Render Free)

To persist the encrypted Telegram login session without a Render Persistent Disk:

1. Create a Firebase Realtime Database and copy its Database URL.
2. In Firebase Project settings → Service accounts, generate a private key JSON.
3. In Render → Environment, add:
   - `FIREBASE_DATABASE_URL` = your Realtime Database URL
   - `FIREBASE_SERVICE_ACCOUNT_JSON` = the complete contents of the service-account JSON file
   - `SESSION_ENCRYPTION_KEY` = a strong secret; keep the same value permanently
4. On Render Free, remove `DATA_DIR=/var/data` if it exists, or change it to `./data`.
5. Redeploy, then log in to Telegram again. Logs should show `Firebase session storage initialized.` and `Encrypted Telegram session saved to Firebase Realtime Database.`

Never commit the service-account JSON or expose it in chat. Firebase Admin SDK credentials bypass Realtime Database Security Rules, so keep the service-account key private and restrict access to Render environment variables.

Important: this change persists the Telegram login session only. SQLite groups, schedules, post history, and uploaded images remain on Render's ephemeral filesystem and may be lost after a restart/redeploy on the Free plan. They need a separate persistent database/storage migration for full persistence.
